# Monitor Scaling & Display Quality

Recovery notes for the external-monitor setup: fractional scaling on HDMI-A-1,
why it kept breaking, and what each fix actually does.

**Most of the files below live outside this repo.** They are not tracked by
anything, so if the machine is reinstalled they are gone. This document exists
so they can be rebuilt from scratch.

## Hardware

| Output | Panel | Native mode | Role |
|---|---|---|---|
| `eDP-1` | AU Optronics 0x829F, 300x190mm | `1920x1200@60.37` | Laptop internal |
| `HDMI-A-1` | Samsung S24E450, 530x300mm | `1920x1080@60.0` | External, i915 driver |

Normal working mode is **external only**: `eDP-1` disabled, `HDMI-A-1` at
`0x0`, scale `0.9375`.

## The Scale Value

`0.9375` makes 1920x1080 present as **2048x1152 logical pixels** — about 7%
more desktop, everything slightly smaller.

Hyprland rejects any scale that does not divide the mode into whole logical
pixels. For 1920x1080 the usable values are:

| Scale | Logical size | Note |
|---|---|---|
| `0.96` | 2000x1125 | subtle |
| `0.9375` | 2048x1152 | **current** |
| `0.8` | 2400x1350 | aggressive |
| `0.75` | 2560x1440 | very aggressive |
| `0.9` | 2133.33x1200 | **rejected** — not a whole number |

To change it, edit **both**:

1. `SCALES['HDMI-A-1']` in `~/.local/bin/monitor-menu`
2. the scale field in `~/.config/hypr/monitor-state.conf`, then `hyprctl reload`

Or just edit `SCALES` and re-pick a mode from the `SUPER+U` menu — the menu
rewrites the state file itself.

## Why Workspace Switching Used To Break

This was the original symptom: change the scale, and suddenly `SUPER+1..9`
appeared to do nothing.

Scaling was never the cause. `hyprland.conf` only had a catch-all
`monitor=,preferred,auto,1.0`, and the `monitors.conf` / `workspaces.conf`
files written by nwg-displays **were never sourced by anything** — they are
inert. So any config edit triggered `hyprctl reload`, the catch-all re-applied
to every output, `eDP-1` came back at 1920x1200, and the workspaces scattered
onto a laptop screen sitting behind a closed lid. The binds worked fine; the
workspaces were just on a display nobody could see.

The fix is `monitor-state.conf`: a real, sourced file that survives reloads.

## Files

### `~/.config/hypr/hyprland.conf`

Two changes near the top.

```conf
# Fallback for any monitor not covered by monitor-state.conf below.
monitor=,preferred,auto,1.0

# Live display state (mode + scale), written by ~/.local/bin/monitor-menu.
# Sourced AFTER the fallback so a reload keeps the current layout instead of
# re-enabling every monitor at scale 1.
source = ~/.config/hypr/monitor-state.conf
```

Order matters. The catch-all stays as a fallback for unknown monitors, and the
state file is sourced *after* it so it wins for the two known outputs.

```conf
# Keeps GTK3 sharp under fractional monitor scaling by rendering at 2x and
# letting the compositor downscale. Mirrors ~/.config/environment.d/95-hidpi.conf,
# which covers the uwsm-app / D-Bus launch path this line does not reach.
env = GDK_SCALE,2
```

`env =` in `hyprland.conf` only reaches direct children of Hyprland. Apps
started through `uwsm-app` or D-Bus activation do not see it, which is why the
same variable is also set in `environment.d` (below). Both are needed.

### `~/.config/hypr/monitor-state.conf` — new

```conf
# Auto-generated by monitor-menu. Sourced from hyprland.conf.
# Do not edit manually — rewritten on every display-mode switch.

monitor=eDP-1,disable
monitor=HDMI-A-1,1920x1080@60.0,0x0,0.9375
```

Rewritten by `monitor-menu` every time a display mode is picked. This is what
makes `hyprctl reload` idempotent.

**The disable line must come first.** If `eDP-1` is still enabled at `0x0` when
`HDMI-A-1` is moved onto `0x0`, Hyprland fires:

> Your monitor layout is set up incorrectly. Monitor eDP-1 overlaps with other
> monitors. Please see the wiki (Monitors page) for more. This **will** cause
> issues.

The final layout was always fine — the warning came from the transient state
mid-parse. Ordering disables first removes it.

### `~/.local/bin/monitor-menu`

The `SUPER+U` display-mode switcher. Four changes.

**1. Scale is configurable instead of hardcoded.** Every mode used to end in a
literal `,1`, so picking any mode silently reset the scale.

```python
SCALES = {
    'HDMI-A-1': 0.9375,
}
DEFAULT_SCALE = 1

def scale_for(name):
    return SCALES.get(name, DEFAULT_SCALE)
```

Also fixed in `extend` mode: the external monitor's x-position is in *logical*
pixels, so it divides by the internal's scale rather than using raw physical
width.

**2. State persistence.** `batch()` now mirrors whatever it applied into
`monitor-state.conf` via `write_state()`, converting `monitor eDP-1,disable`
into `monitor=eDP-1,disable`.

**3. Disables ordered first**, for the overlap warning above:

```python
cmds = tuple(sorted(cmds, key=lambda c: not c.endswith(',disable')))
```

**4. Mode validation in `mon_mode_str()`.** This one caused a real corruption.
`duplicate` mode used to force the *internal's* mode onto the external for
mirroring. While mirroring, `hyprctl monitors` then reports HDMI-A-1 as
`1920x1200` — eDP-1's resolution, which the Samsung panel cannot do. The next
mode switch read that back and persisted it, writing a permanently invalid
`monitor=HDMI-A-1,1920x1200@60.372,...` into the state file.

`mon_mode_str()` now confirms the reported mode against the output's own
`availableModes` before trusting it, and `duplicate` gives each output a mode it
actually supports (Hyprland scales mirrored content itself).

`_restart_axshell()` also passes `GDK_SCALE=2` in the child environment, so a
mode switch does not relaunch the bar unscaled.

### `config/hypr/ax-shell.conf` — in this repo

```conf
exec-once = GDK_SCALE=2 uwsm-app $(python /home/soh4m/.config/Ax-Shell/main.py)
```

Redundant with the global `GDK_SCALE=2` below, and deliberately kept that way:
it is the same value, so there is no conflict, and it keeps the bar sharp if the
global setting is ever removed or a reinstall wipes `environment.d`. This is the
only one of these files that version control actually protects.

### `~/.config/electron-flags.conf` — new

```conf
--disable-features=WaylandFractionalScaleV1
```

Fixes WhatsApp (`elecwhat`, Electron 40) painting into only ~94% of its window
with a dead strip on the right and bottom.

Chromium 140+ enables `WaylandFractionalScaleV1` by default, but Electron then
renders content at `logical_size * 0.9375` while still committing the buffer at
scale 1, with no viewport to stretch it. Measured directly: content was
**1918x1036 inside a 2036x1100 surface** — exactly the scale factor.

Turning the feature *off* makes Electron commit a full-size scale-1 buffer that
Hyprland downscales itself. Measured fill ratio went `0.9375` → **1.0**.

Read by every Arch `electronNN` wrapper that has no version-specific
`electronNN-flags.conf`, so it applies to all Electron apps — they all hit the
same bug.

> **Do not add `--force-device-scale-factor=2`.** Tested and rejected: Electron
> honours it for layout but still commits buffer scale 1, so content overflows
> and gets clipped — half the window renders off-surface.

### `~/.config/environment.d/95-hidpi.conf` — new

```conf
GDK_SCALE=2
```

GTK3 has no `wp-fractional-scale-v1` support at all, so every GTK3 window
commits a scale-1 buffer that Hyprland downscales — soft text everywhere.
`GDK_SCALE=2` makes GTK render at 2x and lets the compositor downscale to native
pixels, which supersamples rather than blurs. The result is arguably sharper
than scale 1 would be.

Set here (systemd user environment) so `uwsm-app` and D-Bus-activated apps get
it; `hyprland.conf` carries the matching line for direct Hyprland children.

Applies on next login. To apply without logging out:

```sh
systemctl --user set-environment GDK_SCALE=2
```

Already-running apps keep their old environment — restart anything that still
looks soft.

## Per-Toolkit Sharpness

| Toolkit | Status at scale 0.9375 |
|---|---|
| Firefox 153 | Native — speaks `wp-fractional-scale-v1`, renders at true 1920x1080 |
| Alacritty 0.17 | Native — same |
| GTK3 (Ax-Shell, nwg tools) | Supersampled via `GDK_SCALE=2` |
| GTK4 / Qt6 | Already fractional-aware; `GDK_SCALE=2` is correct but costs extra VRAM |
| Electron | **6% downscale, permanently.** See below |

Electron is the one real compromise. Chromium will not commit a non-1 buffer
scale here, so its 2036x1100 buffer gets resampled down to 1909x1031. The
alternatives were tested and are worse. Nothing further to extract.

To check whether some other app can scale fractionally, look for the protocol
in its binary:

```sh
strings /usr/lib/libgtk-3.so.0 | grep -c wp_fractional_scale_manager_v1   # 0
strings /usr/lib/libgtk-4.so.1 | grep -c wp_fractional_scale_manager_v1   # 1
strings /usr/bin/alacritty     | grep -c wp_fractional_scale_manager_v1   # 2
```

A `0` means the app will always be downscaled, and `GDK_SCALE`-style
supersampling is the only lever. Note that a non-zero count is necessary but
not sufficient — Electron binds the protocol twice and still commits the wrong
buffer scale, which is exactly the bug documented above.

## Display Quality Beyond Scaling

Checked via `modetest -c` on the i915 connector:

- `Colorspace: Default` — plain RGB, **no** YCbCr 4:2:0/4:2:2 chroma
  subsampling, so no colour fringing on text.
- `max bpc: 8` — matches the S24E450's 8-bit panel exactly, nothing truncated.
- `Broadcast RGB: Automatic` — **unresolved.** On i915, for a CEA timing like
  1920x1080@60 over HDMI, "Automatic" often resolves to Limited 16:235 rather
  than Full, which crushes blacks and washes highlights.

Broadcast RGB cannot be changed from Wayland: setting connector properties
requires DRM master, which Hyprland holds, and there is no equivalent of
`xrandr --set "Broadcast RGB" "Full"`. Confirming which it picked needs root
(`/sys/kernel/debug/dri/1/i915_display_info`).

Practical workaround is on the monitor itself — the S24E450 OSD has **HDMI Black
Level (Normal / Low)**. If blacks look grey, flip it.

## Known Non-Issues

- `~/.config/hypr/monitors.conf`, `monitors.lua`, `workspaces.conf`,
  `workspaces.lua` are nwg-displays output and **are not sourced by anything**.
  They have no effect. Do not trust them and do not bother editing them.
- **Avoid nwg-displays** for this setup. It writes those inert files and then
  triggers a reload, which is what made the original problem look random.

## Rebuilding After A Reinstall

1. Recreate `~/.config/hypr/monitor-state.conf` (contents above).
2. Add the `source =` line and `env = GDK_SCALE,2` to `~/.config/hypr/hyprland.conf`.
3. Recreate `~/.config/electron-flags.conf` and
   `~/.config/environment.d/95-hidpi.conf` (contents above).
4. Restore `~/.local/bin/monitor-menu` and confirm `SCALES` and `write_state()`
   are present.
5. `hyprctl reload`, then verify:

```sh
hyprctl monitors all -j | python3 -c "
import json,sys
for m in json.load(sys.stdin):
    print(m['name'],'disabled=',m.get('disabled'),f\"{m['width']}x{m['height']}\",'scale',m['scale'])"
```

Expected: `eDP-1 disabled= True`, `HDMI-A-1 disabled= False 1920x1080 scale 0.9375`,
no overlap warning, and `SUPER+1..9` switching workspaces on HDMI-A-1.
